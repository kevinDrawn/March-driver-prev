# Custom Board 디버깅 최종 포스트모템 (Part 1/2)

**기간:** 2026-05-04 ~ 2026-05-14 | **대상:** STM32G431CBU6 커스텀 48핀 BLDC 드라이버  
**최종 결과:** ✅ 전체 하드웨어 검증 완료, 보드 자립 동작 확인

> 근본 원인 3가지: (1) Nucleo-G431RB(MB1367) SWD 버스 충돌 (2) HSE 크리스탈 미동작 (3) 하드웨어 납땜 불량

---

## Phase 1: 초기 진단 (5/4~5/13)

### 1.1 MCU 전원핀(VDD/VSS) 납땜 불량

**배경:** STM32 MCU는 VDD/VSS 핀에 3.3V/GND가 직접 연결되어야 동작한다. 외부 파워서플라이로 보드에 3.3V를 넣더라도, MCU 패드가 납땜되지 않았으면 MCU 자체에는 전기가 가지 않는다.

**테스트 방법:** ST-Link가 SWD 연결 시 자동으로 읽어오는 `Target Voltage` 값을 확인.  
이 값은 ST-Link의 T_VCC 핀이 타겟 보드의 3.3V 라인을 직접 읽어서 보고하는 것이다.

**결과:** Target Voltage = **1.07V** (정상: 3.3V)

**해석:** 1.07V는 MCU에 정상 전원이 공급되지 않고 있다는 증거.  
SWD 핀(PA13, PA14)의 내부 보호 다이오드를 통해 기생 전류(back-powering)가 역류하여 MCU가 겨우 1.07V로 떠 있는 상태였다.  
실물 확인 결과, MCU의 VDD/VSS 패드가 **아예 납땜되지 않은 상태**였다.

**조치:** MCU 전원핀 재납땜 → Target Voltage 3.3V 정상화.

---

### 1.2 DRV8316 Buck 12V 출력 및 칩 제거

**배경:** DRV8316 내부에는 Buck 컨버터가 있어 12V 입력을 3.3V 또는 5V로 변환한다. 이를 위해 외부에 인덕터(L1)와 캐패시터(C6)가 필요하다.

**테스트:** 12V 전원 인가 후 FB_SW 핀(Buck 출력)을 멀티미터로 측정.

**결과:** FB_SW에서 **12V** 측정 (정상: 3~5V). Buck이 스위칭하지 않고 12V를 그대로 통과시키고 있었다.

**조치:** DRV8316 칩을 물리적으로 제거하고, MCU+LED만 남긴 최소 구성으로 전환하여 MCU 자체의 동작 여부에 집중하기로 결정.

---

### 1.3 첫 업로드와 "Verified OK" 함정

**테스트:** PlatformIO에서 `pio run -e custom_board_bench -t upload` 실행.

**과정:**  
1. 최초 시도: `Unable to reset target` 에러 → `reset_config none` 플래그 추가
2. 재시도: **`Verified OK`** 출력 — 펌웨어가 플래시에 기록되고 검증까지 통과

**결과:** 하지만 커스텀 보드의 LED1(PB6)은 깜빡이지 않았다.

**당시 해석:** 클럭 설정이나 리셋 문제로 코드가 실행되지 않는 것으로 판단. → **오진.**

**실제 원인 (나중에 밝혀짐):**  
`Verified OK`는 "어딘가의 MCU 플래시에 정상적으로 기록됨"을 의미할 뿐, **어느 MCU**에 기록되었는지는 알려주지 않는다.  
SB9/SB11 때문에 SWD 신호가 Nucleo 온보드 MCU에만 도달했으므로, 펌웨어는 뉴클리오 칩에 기록되고, 커스텀 보드에는 아무것도 들어가지 않았다.

---

### 1.4 시리얼 통신의 함정

**테스트 1:** 커스텀 보드의 USART3(PB10=TX, PB11=RX)에 외부 배선 → 시리얼 수신 **안 됨.**

**테스트 2:** 시리얼 핀을 PA2/PA3(Nucleo VCP 직결)로 변경 → 시리얼 수신 **성공!**  
벤치테스트 결과(LED OK, SPI 0xFFFF, ADC 값 등)가 화면에 출력됨.

**함정:** 이 출력을 커스텀 보드에서 나온 것으로 판단.  
실제로는 **Nucleo 온보드 MCU**가 코드를 실행한 결과였다. PA2/PA3는 Nucleo ST-Link의 VCP(Virtual COM Port)에 물리적으로 직결되어 있으므로, 뉴클리오 MCU가 실행한 `Serial.print()`가 그대로 PC로 전달된 것.

**교훈:** 시리얼 데이터가 나온다고 해서 "커스텀 보드가 동작 중"이라고 단정할 수 없다. **어느 MCU에서** 데이터가 나오는지를 확인해야 한다.

---

### 1.5 SPI 0xFFFF 오진

**테스트:** DRV8316 SPI 레지스터(IC_Status, Control 등)를 읽어보는 벤치테스트 실행.

**결과:** 모든 레지스터에서 `0xFFFF` 반환.  
- `0xFFFF`는 SPI MISO 라인이 항상 HIGH인 상태를 의미한다.  
- 이는 (a) 칩이 응답하지 않거나 (b) MISO가 풀업되어 있거나 (c) 칩이 아예 연결되지 않았을 때 발생.

**당시 결론:** "SDO(PB4) 납땜 불량" → MCU 재납땜 작업 수행.

**실제:** 이 테스트는 Nucleo 온보드 MCU에서 실행되었다. Nucleo MCU의 PB4에는 DRV8316이 물리적으로 연결되어 있지 않으므로 0xFFFF는 **당연한 결과**였다. 완전한 오진.

---

### 1.6 HSE 클럭 불일치

**배경:**  
- Nucleo-G431RB의 Arduino 프레임워크는 `variant_NUCLEO_G431RB.h`에서 `HSE_VALUE=24000000`을 하드코딩한다.  
- 이는 Nucleo 보드가 ST-Link MCO 출력(24MHz)을 HSE 소스로 사용하기 때문.  
- 커스텀 보드는 독립 크리스탈 16MHz를 사용 → PLL 분주비 불일치.  
- PLL 설정: `M=/6, N=x85, R=/2` → 24MHz 기준 계산. 16MHz 입력 시 VCO 입력 = 2.67MHz (유효 범위 밖) → PLL 잠금 실패 → `Error_Handler()` 무한루프.

**조치:**  
1. `patch_hse.py` 스크립트로 `HSE_VALUE`에 `#ifndef` 가드 추가 → 16MHz 설정 우선 적용
2. `SystemClock_Config`를 HSI(내부 16MHz) 전용으로 오버라이드

**결과:** 빌드/업로드 성공, 하지만 LED1 여전히 안 깜빡임 → 근본 원인은 클럭이 아닌 SWD 라우팅.

## Phase 2: SWD 버스 분석 (5/13~5/14)

### 2.1 이중 MCU 문제 발견

**테스트:** OpenOCD로 MCU의 PKG 레지스터(주소 `0x1FFF7500`)를 읽어서 현재 접속된 칩의 패키지 타입을 확인.

**방법:** `mdw 0x1FFF7500` 명령 → 반환값 `0xffffff00`

**해석:**  
- 하위 8비트 = `0x00` = **LQFP64** 패키지 = Nucleo 온보드 MCU (STM32G431RBT6)
- 커스텀 보드 MCU(STM32G431CBU6)는 **UFQFPN48** 패키지 → 이 값이 달라야 함
- **결론:** SWD가 커스텀 보드가 아닌 Nucleo 온보드 MCU에만 연결되어 있었음

---

### 2.2 SB9/SB11 — 왜 뉴클리오가 신호를 가로채는가

**기술적 배경:**  
Nucleo-G431RB의 기판 모델명은 **MB1367**이며, 이 보드의 SWD 신호 경로는 다음과 같다:

```
ST-Link V3E 칩
    ├── SB9 (0Ω) ──→ 온보드 MCU PA14 (SWCLK)
    ├── SB11(0Ω) ──→ 온보드 MCU PA13 (SWDIO)
    └── CN4 헤더 ──→ 외부 커스텀 보드 (J1)
```

SB9/SB11은 **0옴 저항(솔더 브릿지)**으로, CN4와 온보드 MCU가 **병렬 연결**되어 있다.  
ST-Link가 SWD 명령을 보내면 **두 MCU 모두** 신호를 받지만, 온보드 MCU가 먼저 ACK를 보내므로 ST-Link는 온보드 MCU와만 통신한다.

**구형 보드(MB1136)와의 차이:**  
구형 Nucleo-64 보드에는 **CN2 점퍼**가 있어서 손으로 뽑으면 온보드 MCU가 SWD에서 분리되었다. MB1367에서는 이 점퍼가 **삭제**되고 0Ω 저항으로 대체됨. 인두기 없이는 분리 불가.

**근거 링크 (ST 공식 커뮤니티):**
- https://community.st.com/t5/stm32-mcus-boards-and-hardware/can-a-nucleo-g474re-program-an-external-target-via-cn4/td-p/242646
- https://community.st.com/t5/stm32-mcus-boards-and-hardware/using-nucleo-board-st-link-for-external-stm32/td-p/739875

### 2.3 소프트웨어 SWD 격리 시도 (3회 실패)

**목표:** Nucleo 온보드 MCU의 PA13/PA14를 소프트웨어로 GPIO 모드로 전환하여 SWD에서 "빠지게" 만든 후, 커스텀 보드 MCU만 SWD에 남기는 것.

| 시도 | 방법 | 결과 | 실패 원인 |
|------|------|------|-----------|
| 1차 | PKG=0x02 가정 → GPIO 전환 | 양쪽 SWD 비활성화, 벽돌 | PKG 값 오류 (실제 0x00) |
| 2차 | PKG=0x00, PA13/14 PULLDOWN | Nucleo SWD OFF → 커스텀 접근 불가 | 풀다운이 SWDIO의 정상 풀업과 충돌 |
| 3차 | PKG=0x00, PA13/14 ANALOG(Hi-Z) | Nucleo SWD OFF → 여전히 접근 불가 | Hi-Z로도 버스에 커스텀 보드 안 잡힘 |

**교훈:** SB9/SB11이 0Ω으로 하드와이어링되어 있으므로, 소프트웨어로 한쪽 MCU를 "떼어내도" 전기적으로 여전히 연결된 상태. 물리적 분리(디솔더링 또는 독립 프로그래머)만이 답.

---

### 2.4 BOOT0(PB8) — 왜 GND에 연결해야 하는가

**기술적 배경:**  
STM32의 BOOT0 핀은 MCU가 리셋 후 **어디서 코드를 실행할지** 결정한다:
- `BOOT0 = LOW(GND)` → **Flash 메모리에서 부팅** (우리가 넣은 펌웨어 실행)
- `BOOT0 = HIGH(3.3V)` → **내장 부트로더 모드** (UART/CAN으로 명령 대기, 우리 코드 실행 안 함)
- `BOOT0 = 플로팅` → **불확실** — 노이즈에 따라 어느 쪽으로든 갈 수 있음

**커스텀 보드 상태:** PB8(BOOT0)이 CAN_RX_BOOT 네트에 연결되어 있었으나 미납땜 → **플로팅**.  
플로팅 상태에서 MCU가 부트로더 모드로 들어가면, 플래시에 펌웨어가 있어도 실행되지 않는다.

**조치:** BOOT0를 GND에 **납땜 고정**. → 이후 F767ZI 테스트 시 MCU가 Flash에서 정상 부팅.

> 참고: STM32G4는 옵션 바이트(nBOOT_SEL, nBOOT0)로 BOOT0 핀을 무시하도록 설정할 수도 있다. 기본값은 "BOOT0 핀 사용"이므로 물리적 GND 연결이 가장 안전.

---

### 2.5 NRST 풀업(R3) 납땜

**배경:** NRST 핀이 플로팅이면 MCU가 간헐적으로 리셋될 수 있다. MCU 내부에 약한 풀업(~40kΩ)이 있지만, 노이즈 환경에서는 불충분.

**조치:** 회로도의 R3(풀업 저항) 납땜 추가.  
**결과:** SWD 동작 변화 없음 — 이 문제의 근본 원인은 아니었으나, 안정적 동작을 위해 필요한 조치.

---

### 2.6 SWD 직접 GPIO 제어 테스트 (결정적 증거)

**목적:** "펌웨어 코드가 잘못되어서 LED가 안 켜지는 것"인지, "MCU 자체에 접근이 안 되는 것"인지를 구분.

**방법:** OpenOCD로 MCU를 halt한 상태에서, 펌웨어를 전혀 거치지 않고 **레지스터에 직접 값을 기록**하여 PB6을 강제로 HIGH로 만듦:

```
# 1) GPIOB 클럭 활성화
mww 0x4002104C 0x00000002

# 2) PB6을 출력 모드로 설정
mww 0x48000400 0x00001000

# 3) PB6 HIGH
mww 0x48000418 0x00000040
```

**결과:**  
- **Nucleo 보드의 LD1(PB6):** 켜짐  
- **커스텀 보드의 LED1(PB6):** 0V, 반응 없음

**해석:** 이 테스트는 플래시 메모리의 펌웨어를 **1줄도 실행하지 않는다.** 클럭이 안 맞든, 코드가 꼬였든 상관없이 MCU 레지스터에 직접 값을 쓰는 것이다.  
커스텀 보드가 반응하지 않았다는 것은 **SWD 명령 자체가 커스텀 보드 MCU에 도달하지 못하고 있다**는 물리적 증거이며, 이로써 "펌웨어 문제" 가능성이 **완전히 배제**되었다.
